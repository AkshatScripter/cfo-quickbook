# QB Customer Assignment — Design Spec

**Status:** Approved  
**Date:** 2026-06-02

---

## Problem

When a user signs up as a `customer` role, their `cfo_users` row has:
- `companyId = null` — no link to a company owner
- `name` = whatever they typed at signup

The customer invoices API (`GET /api/customer/invoices`) fails silently on both: it bails on null `companyId` and even if that were fixed, it matches invoices by `customerName = user.name` — fragile, breaks if the name doesn't exactly match a QB customer display name.

---

## Solution

Add `qbCustomerId` to `cfo_users`. The company owner assigns each portal customer to a specific QB customer via a dropdown on the `/customers` page. The invoice API then uses the reliable QB ID for lookup instead of name matching.

---

## Data model change

```ts
// cfo_users — one new nullable column
qbCustomerId: text("qb_customer_id")  // FK to cfo_qb_customers.qb_id (logical, not enforced)
```

No new table. `companyId` (already exists) stays as the company link.  
`qbCustomerId` stores the `qbId` value from `cfo_qb_customers` — e.g. `"123"`.

> **POC note:** `companyId IS NULL` customers are shown to any company owner (since there is no invite system yet). This is acceptable for a single-company POC. A future invite flow would scope visibility properly.

---

## API changes

### `GET /api/customers` — extended
Currently: returns only customers where `companyId = user.id`.  
After: returns customers where `companyId = user.id` **OR** `companyId IS NULL` — so the company owner can see and assign unlinked signups.

Response shape gains two fields per row:
```json
{ "qbCustomerId": "123" | null, "companyId": "uuid" | null }
```

### `PATCH /api/customers/[id]` — new
Company owner assigns a QB customer to a portal user.

```
PATCH /api/customers/:id
Authorization: company role
Body: { "qbCustomerId": "123" }  // QB customer's qbId, or null to unlink

Sets on cfo_users row:
  qbCustomerId = body.qbCustomerId
  companyId    = caller's user.id  (if not already set)
  updatedAt    = now()
```

Returns the updated user row.

### `GET /api/customer/invoices` — updated lookup
Replace the name-match with a QB ID match:

```ts
// before (fragile):
WHERE customerName = user.name

// after (reliable):
WHERE customerId = user.qbCustomerId
```

Also add a guard: if `qbCustomerId` is null, return `{ invoices: [], totalOwed: 0, notLinked: true }` so the UI can show a helpful message instead of just empty data.

## UI changes — `/customers` page

The page gets two stacked sections:

### Section 1 — Portal users
Shows all portal customers visible to this company (`companyId = user.id` or null).

| Column | Value |
|---|---|
| Name / Email | From `cfo_users` |
| Assigned QB customer | Dropdown of `cfo_qb_customers.displayName`; blank if unlinked |
| Status | "Linked ✅" or "Not linked" |

Behaviour:
- Dropdown lists all QB customers for the company's realm, sorted by `displayName`
- Selecting a QB customer immediately calls `PATCH /api/customers/:id` and shows a success toast
- Selecting blank (—) unlinks (`qbCustomerId = null`)
- Rows are sorted: unlinked first, linked last

### Section 2 — QB customers (existing)
Unchanged from the current implementation — shows synced QB customer rows with balance etc.

## Customer portal — improved empty state

When `notLinked: true` is returned by the invoices API, the customer dashboard shows:

> "Your account hasn't been linked to a company yet. Contact your account manager to get set up."

Instead of a blank page.
